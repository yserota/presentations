The Problem
Where We Started
The Documentation Pain Points
Before we introduced agentic AI, every phase of the documentation lifecycle had a bottleneck that was entirely manual.
🔴 Discovery was a bottleneck
Every new feature required writers to schedule SME interviews, chase HLD links on Confluence, and manually find Figma screens — often days after R&D had already moved on.
🔴 Sprint planning excluded TW
Writers were not part of PI planning. Documentation scope was never estimated. Surprise workload spikes were the norm at every sprint boundary.
🔴 12-day average cycle time
From ticket creation to published doc, the average was 12 days. Manual drafting, review rounds with unresponsive SMEs, and no automated validation kept PRs open indefinitely.
🟡 Tools were completely siloed
Jira, Confluence, Figma, and GitHub had no shared context. Writers context-switched constantly and still produced incomplete drafts because no single tool had the full picture.
🟡 Tickets created too late
Documentation tickets often arrived near R&D code freeze with no attached context — no Figma, no HLD, no PRD references. Writers started cold every time.
🟡 No measurement
We had no reliable way to measure demand vs. capacity. Were writers overloaded or underloaded? We couldn't tell. Strategic decisions were based on gut feel, not data.

The Core Insight

AI doesn't help if it doesn't understand your workflow, your tools, and your data. A generic prompt is not a skill. A skill is a structured agent workflow with defined inputs, outputs, and validation — built for your specific pipeline.

The Key Principle

Skills, not prompts. A skill knows where to look for context, what to do with it, how to validate the output, and when to hand off to a human. It's the difference between an ad-hoc experiment and an operational capability.

North Star: All documentation flows automatically from R&D/PM artifacts to agent-ready, published content — without manual handoffs. TW is the human reviewing, approving, and raising quality.
The Platform
Infrastructure
Why We Chose Cursor as Our AI IDE

Agent Mode

Cursor's agent mode lets you build multi-step autonomous tasks — not just one-shot prompts. The agent reads files, searches repos, calls external APIs, creates PRs, and updates Jira — all in one run.

Skills = Reusable Workflows

A Cursor "skill" is a structured SKILL.md file that instructs the agent. Skills are versioned, shared across the team, and contributed back to a central library — making every writer's agent smarter over time.

MCP: Connecting Every Tool

Model Context Protocol (MCP) connects Cursor to any tool via a policy-controlled broker. One agent can read a Jira ticket, pull a Confluence HLD, fetch a Figma screen, clone a GitHub repo — in a single workflow.

Tools connected via MCP Policy Broker
Jira (tickets, sprints) Confluence (HLDs, specs) GitHub (code, PRs) Figma (UI designs) Google Drive / Gmail Google Calendar Asana (tasks) Aha! (roadmap)
“Before Cursor, I'd spend 30 minutes finding the right Figma file, Confluence page, and Jira ticket. Now the agent gathers all of that before I've finished my coffee.”
Foundation move: MadCap Flare → MkDocs

The migration from Flare to Markdown/MkDocs was not just a tooling change — it was the prerequisite for AI-native workflows. Markdown is agent-readable. YAML frontmatter enables automated tagging. CI/CD enables automated validation.

Deep Dive
TW Feature Doc — How It Actually Works
From Jira Ticket to Draft Doc in One Command
What the writer does
1
Writer
Opens Cursor, types /tw-feature-doc with the Jira ticket ID. That's it.
2
Agent: Context Gathering
Pulls Jira ticket details, linked Confluence HLDs, attached Figma designs, and referenced GitHub branches automatically via MCP connections.
3
Agent: Style + Structure
Reads the Palo Alto Networks style guide, identifies the correct doc type and template, maps the content architecture, and applies heading/tone conventions.
4
Agent: Draft Generation
Writes the complete Markdown doc: overview, prerequisites, procedures, and troubleshooting sections. Embeds correct YAML frontmatter for agent-readiness.
5
Writer: Review & Refine
Writer reviews the draft, focuses on information architecture decisions, accuracy edge cases, and quality of user experience — not drafting from scratch.

Inputs the skill pulls automatically

Jira ticket (scope) Confluence HLD (how it works) Figma screens (UI) GitHub branch (implementation) Style guide (conventions) Existing docs (context)

What comes out

A complete Markdown file with correct headings, procedures, and YAML frontmatter. Ready for writer review — not a starting outline, a working draft that addresses all the requirements in the Jira ticket.

The impact

Discovery + first draft: from 2–3 days of manual work to under 30 minutes. Writer time shifts from drafting to reviewing, improving information architecture, and surfacing gaps the agent couldn't see.

It's Not Just About Writing
AI Across the Whole TW Operation
Once you have the infrastructure and the MCP connections, AI can augment every part of how a TW team operates — not just authoring.

The DCI (Demand-Capacity Index) pipeline automatically fetches Jira sprint data, computes SP-weighted throughput per writer, and publishes a live Google Sheets dashboard. We now know, to the data, when the team is overloaded — before it becomes a crisis.

🗓️ Day Management

The Day Manager skill ingests emails, calendar events, and Jira to surface the day's priorities, prep 1:1 talking points, and recommend focus blocks. A morning routine that used to take 45 minutes now takes 5.

📋 Program Operations

The Supportability Plan skill pulls all Jira tickets with the "Supportability" label, updates the Confluence program page, and tracks milestones automatically. Program reviews now take minutes to prepare.

🎫 QBR Prep

Before quarterly reviews with leadership, the agent pulls live data from Jira, DCI dashboards, and doc health reports to auto-build a full slide deck. Data-driven presentation preparation in one command.

🏷️ Jira Operations

Sprint planning, ticket assignment, writer workload views — all accessed through natural language queries to Jira via MCP. "Which tickets are in sprint 2701, by writer?" is answered instantly.

🔗 Guild & Community

The agent surfaces relevant topics for the weekly TW Global Guild meeting by scanning open Confluence discussions, recent Jira activity, and style guide questions — making facilitation effortless.

What We Learned
Honest Reflection
Lessons Learned
✅ Infrastructure first
The Flare → MkDocs migration was painful and unglamorous, but it was the prerequisite for everything else. Agents need structured, readable content. You can't build AI-native workflows on legacy binary file formats. Invest in the foundation before the features.
✅ Start with one skill, make it excellent
We spent months making TW Feature Doc really good before we built anything else. The temptation is to build ten mediocre automations. Resist it. One skill that writers trust and use daily is worth more than ten that get tried once and abandoned.
⚠️ Connect your tools — or the AI has no data
The MCP Policy Broker was the unlock. Without it, the agent could only see what was in the local repo. With it, every tool in the TW ecosystem becomes a data source. Tool connectivity is not optional — it's the prerequisite for context-aware AI.
⚠️ Human in the loop is a feature, not a compromise
We deliberately kept the writer in the approval loop. Not because we couldn't automate it — because a writer who reviews an agent-generated draft learns what the agent does well and where it needs more guidance. That feedback loop is how skills improve over time.
💡 Measure before you optimize
We didn't know our cycle time was 12 days until we measured it. We didn't know we were running above DCI 1.0 until the pipeline told us. Build your measurement infrastructure first — it shapes every decision about where to apply AI energy.
💡 Your team IS the AI strategy
The writers who learn to work with agents — to write good prompts, to recognize great output from mediocre output, to build and share skills — are the competitive advantage. AI tools commoditize. A team that knows how to use them does not.
For You
Practical Advice
What You Can Take Home Today
01
Start with your workflow, not the AI
Map your documentation lifecycle before you touch any AI tool. Where are the bottlenecks? Where does manual context-gathering kill momentum? Build skills for those specific pain points — not generic "AI writing helpers."
02
Build skills, not prompts
A prompt dies in a chat window. A skill lives in a version-controlled file, is shared with your whole team, improves over time, and works the same way every time. If you find yourself copying a prompt across sessions, turn it into a skill.
03
Connect your tools before you build features
AI is only as smart as the data it can see. Before investing in sophisticated automations, invest in tool connectivity (MCP, integrations, APIs). An agent that can read your Jira, Confluence, and GitHub is fundamentally more capable than one that can't.
04
Measure the right things
Cycle time. Demand-capacity ratio. Skill adoption rate. Agent acceptance rate. These are the metrics that tell you whether AI is actually changing your operation — not "how many times did writers use AI this month."
05
The role doesn't disappear — it elevates
Every AI tool that handles drafting, formatting, and validation frees a writer to do the thing AI cannot: understand the user's mental model, anticipate confusion, make strategic information architecture decisions. That's the job of the future.
